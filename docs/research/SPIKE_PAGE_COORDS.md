## 2. Як InkCanvasView зараз перераховує координати

`InkCanvasView.getScaledStrokes(pageWidthPt, pageHeightPt)` (InkCanvasView.kt, наприкінці файлу):

```
scaleX = pageWidthPt  / canvas.width
scaleY = pageHeightPt / canvas.height
pt' = (pt.x * scaleX, pt.y * scaleY)
```

Тобто **весь екран полотна ототожнюється з усією сторінкою**. Полотно — `match_parent` над контейнером переглядача (`activity_reader.xml`, `inkCanvasView`). Сторінку вибирає `ReaderActivity.saveDrawingToDocument`: `pageIndex = viewerFragment.currentPageIndex` = `PdfView.firstVisiblePage` (ReaderActivity.kt:290, VolumPdfViewerFragment.kt:19-20).

Висновок: **некоректно** майже в усіх реальних випадках.

| Ситуація | Що відбувається |
|---|---|
| Масштаб ≠ «сторінка точно на весь екран» | Сторінка у PdfView має поля/проміжки й свій `zoom` (px на pt). Полотно їх не знає → штрих зміщений і розтягнутий. |
| Різні пропорції екрана і сторінки | `scaleX ≠ scaleY` → штрих спотворюється (товщина береться як середнє, форма — ні). |
| Скрол | Зсув `scrollX/scrollY` ігнорується. Штрихи фіксовані у координатах екрана, а не контенту. |
| Зум | Те саме: `zoom` не враховується. |
| Кілька сторінок на екрані | `firstVisiblePage` — перша **частково** видима сторінка (PdfView.kt:488, коментар «including partially-visible»). Це може бути смужка 5 px угорі. Усі штрихи пишуться на неї. Штрих, що перетинає межу сторінок, не розбивається. |
| Інше | Під час малювання полотно перехоплює дотики (повертає `true` на DOWN), тож скрол/зум заблоковані — це маскує проблему лише для одного «кадру». |

Окремо (стосується ядра, не UI) — `PdfBoxAnnotationEngine` перетворює y так: `pdfY = pageHeightPt - y` (рядки 86, 190, 243). `ReaderActivity.getPageDimensions` бере розмір з `cropBox ?: mediaBox` (ReaderActivity.kt:473). Але:
- зсув початку `cropBox`/`mediaBox` (lowerLeft ≠ 0,0) не додається;
- `/Rotate` сторінки не враховується.
На сторінках із поворотом або нульовим початком, відмінним від (0,0), координати будуть хибні **навіть при ідеальному вхідному (x,y)**. Це окремий дефект, його теж треба закрити у будь-якому варіанті розв'язання. Перевірено лише читанням; на реальних файлах НЕ ПЕРЕВІРЕНО.

## 4. Висновок

**Координати отримати можна.** Для цільового сценарію «тап → (pageIndex, x, y) у pt» достатньо публічного API:

```kotlin
pdfView.viewToPdfPoint(event.x, event.y)  // PdfPoint? : pageNum, x, y у pt, початок зверху-ліворуч
```

Умови:
1. координати `event.x/y` мають бути у системі координат самого `PdfView` (не екрана і не іншого оверлея; якщо оверлей зсунутий — компенсувати);
2. `null` слід обробляти (тап у проміжку між сторінками);
3. `PdfPoint.y` відраховується **зверху**, як і `FreeTextData.y` у контракті → інверсію Y вже робить `PdfBoxAnnotationEngine`, додатково перевертати не треба;
4. потрібен відповідний захоплювач дотику (див. нижче) — публічного tap-слухача в бібліотеці немає;
5. розбіжності розміру сторінки (Int vs Float із PDFBox, `cropBox`, `/Rotate`) треба звірити на реальних файлах.

**Не можна** (публічно): використати вбудований режим анотацій бібліотеки; розраховувати на це як на запасний варіант не слід.

## 5. Варіанти (вибір — за Керівником проєкту)

### A. Тонкий шар над фрагментом + `viewToPdfPoint`
Режим «поставити»: слухач дотику на `PdfView` (`setOnTouchListener`) або прозорий оверлей, що пересилає жести. Тап → `viewToPdfPoint` → `FreeTextData(x,y)` / ✓ / ✗. Прев'ю маркера малюється через `pdfToViewPoint` і `OnViewportChangedListener`. Малювання (`InkCanvasView`) переписується на `viewToPdfPoint` для кожної точки (сторінка береться з першої точки).
- **Плюси:** зберігається системний пошук, виділення тексту, посилання, швидкість; без нових залежностей; зміни локальні (`app` + дрібниця в `core-pdf`).
- **Мінуси:** залежимо від `@ExperimentalPdfApi` у beta (API може змінитись); tap-перехоплення неофіційне (конфлікт з жестами бібліотеки — НЕ ПЕРЕВІРЕНО); після збереження документ перезавантажується (`documentUri = null → uri`, ReaderActivity.kt:449-455) — збереження скролу/зуму НЕ ПЕРЕВІРЕНО, для UX «тап — і з'явилось» це може бути помітно; Android 9–11 не покритий.
- **Обсяг (моя оцінка, не вимір):** ~2–4 робочі дні: захоплювач і прев'ю (1–1.5), переписування ink (0.5–1), ✓/✗ як нові елементи в `core-pdf` (0.5–1, зміна CONTRACTS), виправлення `cropBox`/`/Rotate` + тести на повернутих PDF (0.5–1), перевірка на S24 Ultra.

### B. Власний `PdfView` без фрагмента (використати публічний `PdfView` напряму)
Піднімаємо `PdfView` самі, лише з `PdfDocument`; решту UI (пошук, панель) робимо свою.
- **Плюси:** повний контроль над жестами й життєвим циклом; не залежимо від протектед-обмежень фрагмента.
- **Мінуси:** потрібно створювати/відкривати `PdfDocument` (публічний шлях для цього без фрагмента — НЕ ПЕРЕВІРЕНО; у вихідниках `SandboxedPdfDocument` бачу як конкретний клас сервісу, чи він доступний застосунку — не з'ясовано); власний UI пошуку, пароля, помилок. Дублює вже готове у фрагменті.
- **Обсяг:** ~1–2 тижні (оцінка), більша частина — відтворення UI фрагмента й тестування паролів/помилок.

### C. Власний рендер через `PdfRenderer`
- **Плюси:** повний контроль координат (самі рахуємо масштаб/зсув); працює на API 28+; не залежимо від beta.
- **Мінуси:** втрачаємо **пошук, виділення тексту, посилання, форми-віджети, швидкий скрол, тайлінг** (у `PdfRenderer` на API <35 лише растр сторінки; `androidx.pdf` саме це й додає). Самі пишемо масштабування, плавний скрол, кеш тайлів, керування пам'яттю (великі файли, сотні сторінок за MASTER_SPEC «Якість»). Текстовий шар можна отримати лише через PDFBox (`PDFTextStripper`) — повільно й не збігається за геометрією з растром.
- **Обсяг:** ~3–5 тижнів (оцінка) до паритету з поточним переглядачем; суперечить затвердженому R2 і MVP-вимозі «пошук і виділення тексту».

(Варіант «чекати публічного API анотацій від androidx.pdf» не розписую: дати й обсяг у вихідниках не знайдено, офіційні нотатки релізів не перевірялись — НЕ ПЕРЕВІРЕНО.)

## 6. Що має вирішити Керівник проєкту

1. Який варіант (A / B / C) затверджується; чи допустима залежність від `@ExperimentalPdfApi` у beta.
2. Чи розширювати CONTRACTS (v0.4): ✓/✗ як окремий метод `AnnotationEngine` чи як символ у `FreeTextData` (потрібен шрифт, що має ✓/✗ — зараз `PDType1Font.HELVETICA` + WinAnsi, символів немає; ZapfDingbats — один з варіантів, НЕ ПЕРЕВІРЕНО).

## 8. Перевірка на пристрої

Дата: 2026-11-07. Пристрій: Galaxy S24 Ultra (SM-S928B), Android 17 (SDK 37), екран 1440×3120. Код і PDF — лише в `spike/` (у `.gitignore`, не в git). Production-код не змінювався.

**Метод.** Окремий спайк-застосунок (`com.savoj.volumpdf.spike`, ті самі версії залежностей, що в `core-pdf`/`app`; для теми додано `material:1.12.0`, він уже є в `app`). Для випадку 3 перший прогін дав y на ~6,6 pt менше: скрол змінився 1200 → 1184 між скріншотом і тапом (моя гонка). Повтор із очікуванням стабілізації скролу дав значення з таблиці.

Висновки за таблицею:
- `viewToPdfPoint` дає правильні `pageNum`, `x`, `y` (pt, початок зверху-ліворуч) при скролі, зумі і кількох сторінках на екрані. У цьому вікні `view == raw` (View на весь екран).
- `firstVisiblePage` не є сторінкою тапу (у випадку 3 `firstVisible=0`, а тапи по сторінці 1) — сторінку треба брати з `PdfPoint.pageNum`.
- **`/Rotate 90`:** координати — у відображеній (повернутій) системі, початок — лівий верхній кут повернутої сторінки. Для PDFBox (нерухомий user space) потрібне перетворення. Для 90° за годинниковою: `x_user = y_view`, `y_user(знизу) = x_view`; перевірено на A: (742, 100) → (100, 742) ✓. 180° і 270° НЕ ПЕРЕВІРЕНО.
- **CropBox:** початок координат — лівий верхній кут CropBox, а не MediaBox. Для PDFBox: `x_user = crop.llx + x`, `y_user(знизу) = crop.ury − y`; перевірено: (100, 100) → (200, 600) ✓. Тобто дефект із розд. 2 (`PdfBoxAnnotationEngine` не враховує зсув CropBox і `/Rotate`) підтверджений на реальному файлі як потреба в перетворенні; саме `PdfBoxAnnotationEngine` на цих файлах не запускався.
- `setOnTouchListener` (повертає `false`) працює: тапи приходять, свайп-скрол працює (0 → 2473 px). Конфлікту зі скролом не виявлено.

### Скрол і зум після `documentUri = null; documentUri = uri`

Перевірено послідовність із `ReaderActivity.reloadViewerDocument` у спайк-реплікі (сам `ReaderActivity` не запускався).

| Дія | Результат |
|---|---|
| `null` → той самий `uri` | **Перезавантаження не відбувається**: `onLoadDocumentSuccess` не викликався; zoom і скрол без змін (2,42; scrollY 105338). Після підміни вмісту файла під тим самим URI на екрані лишився старий вміст. |

### 9.7. Що має вирішити Архітектор

1. **Ink.** `PdfView` не показує `/Ink` від `PdfBoxAnnotationEngine` (навіть із суцільним AP).
