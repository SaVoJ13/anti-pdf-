# План: дзеркальні EXIF Orientation 2/4/5/7 в `imagesToPdf` і `appendFiles`

Статус: дослідження, код не змінювався. База: `origin/main` `c65e367`. НЕ ПЕРЕВІРЕНО на телефоні і на реальних файлах.

## 1. Поточний стан
- `ExifOrientation.read` повертає 1..8; `rotationDegrees` відображає 3,4->180, 6,7->90, 8,5->270, решта 0. Для 2,4,5,7 дзеркало ігнорується (коментар у файлі).
- `PdfBoxPageOperationsEngine.imagesToPdf` (рядки ~272-283): кут = EXIF + ручний, `page.rotation = rotation`, зображення малюється `drawImage(x, 0, 0, width, height)` без матриці. `appendFiles` (~735-742) робить так само.
- Наслідок: фото з фронтальної камери або після деяких редакторів (мітка 2/4/5/7) у PDF виходить віддзеркаленим (текст «навпаки»).

## 2. Як підтримати
1. Чиста функція в `ExifOrientation`: `transform(orientation): Pair<Int /*кут за год.*/, Boolean /*flipH*/>`. Таблиця: 1:(0,ні) 2:(0,так) 3:(180,ні) 4:(180,так) 5:(270,так) 6:(90,ні) 7:(90,так) 8:(270,ні). Тут 4 = дзеркало по вертикалі = поворот 180 + flipH. `rotationDegrees` лишити (сумісність і тести).
2. Ручний поворот додається до кута як зараз: `/Rotate = (exifDeg + manual) % 360`. /Rotate обертає готову сторінку разом із вмістом, тому дзеркало живе лише в матриці малювання, а ручний поворот лишається «за годинниковою» на екрані.
3. Малювання: замість `drawImage(x, 0f, 0f, w, h)` при flipH=true: `cs.drawImage(x, Matrix(-w, 0f, 0f, h, w, 0f))` (PDFBox `Matrix(a,b,c,d,e,f)`; дзеркало по X у межах MediaBox `0..w`). `w,h` — розміри MediaBox до `/Rotate` (як зараз з `pageSizePt`).
4. Перевірка впливу `/Rotate`: схема «дзеркало в матриці, потім /Rotate = кут» відповідає порядку «спочатку flipH, потім поворот». У прикладах Android `ExifInterface` TRANSPOSE/TRANSVERSE (5/7) описують як «поворот, потім дзеркало»; для 5 і 7 ці порядки дають різні картинки (дзеркало по іншій осі). Для 2 і 4 розбіжності немає. Тому для 5 і 7 обов'язково звірити з еталонами (п. 4-5); якщо розходиться, замінити flipH на flipV (`Matrix(w,0,0,-h,0,h)`) для 5 і 7.
5. Сигнатури API без змін; змінюється лише внутрішнє малювання. Логіку «EXIF -> (кут, flip)» винести в одне місце для обох викликів.

## 3. Ризики
- Хибний порядок для 5 і 7 (п. 2.4): фото віддзеркалене по хибній осі. Головний ризик; лікується еталонними файлами.
- PNG/WebP/HEIC без обробки EXIF лишаються як є.
- Для 5-8 ширина/висота сторінки міняються через `pageSizePt` (вже є для 90/270) - не зламати.
- Мініатюра у списку «Зображення у PDF» не враховує EXIF і дзеркало, тому може відрізнятися від PDF (для кута це вже так; дзеркало посилить розбіжність).
- Вихідний JPEG не змінюється; розмір PDF не змінюється.

## 4. Тести
Юніт (core-pdf, чиста логіка): таблиця `transform` для 1..8 і значень поза діапазоном; `rotationDegrees` без змін.
Інтеграційні (PDFBox на JVM, як наявні тести `imagesToPdf`): синтетичний JPEG 3x2 з різними кольорами кутків і зібраним у тесті EXIF-сегментом для кожної орієнтації 1..8; відрендерити сторінку (`PDFRenderer`) і порівняти кутові пікселі з очікуваними; перевірити `/Rotate` і MediaBox. Мутація: прибрати flip у матриці -> тести 2/4/5/7 червоні; змінити знак для 5/7 -> червоні.

## 5. Що перевірити на реальних фото (телефон)
Селфі з фронтальної камери (мітка залежить від виробника), фото з камери у 4 положеннях телефона, файл з міткою 4 з редактора, фото з текстом чи стрілкою для оцінки на око, JPEG без EXIF, JPEG з обрізаним EXIF. Кожне: у «Зображення у PDF», у скані (галерея) і при додаванні до наявного PDF (`appendFiles`); окремо разом із ручним поворотом на 90.

## 6. Обсяг
Малий-середній, близько 0.5-1 дня. Код ~40-60 рядків (`ExifOrientation.transform`, правка двох місць малювання), тести ~100-150 рядків, одна ітерація на еталонних файлах для 5/7. Нових залежностей, дозволів, рядків інтерфейсу немає. Зміна поведінки core-pdf без зміни сигнатур; потрібен запис у `docs/CONTRACTS.md`.
