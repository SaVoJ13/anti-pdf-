## Деталі по питаннях

### 1. Варіант A

B (1–2 тижні) і C (3–5 тижнів, втрата пошуку й виділення) дорожчі, а A уже підтверджений вимірами на пристрої. Ризик у тому, що API експериментальний. Тому єдиний клас-обгортка і зафіксована версія.

Для вашої вимоги «додане рухається до збереження» мало `viewToPdfPoint`. Потрібен ще зворотний напрямок: де на екрані зараз точка сторінки. Тоді оверлей «липне» до сторінки під час зуму й скролу. У спайку перевірено лише `viewToPdfPoint`, а існування й точність зворотного перетворення **НЕ ПЕРЕВІРЕНО**. Це перший пункт міні-спайку (Етап 0).

### 2. Шрифт

- **Roboto.** `OFL.txt` у `google/fonts/ofl/roboto` я прочитав на GitHub: SIL OFL 1.1, «Copyright 2011 The Roboto Project Authors», застереженого імені шрифту (Reserved Font Name) немає. Стара інформація «Roboto = Apache» застаріла: релізи 2020 року перелицензовано з Apache на OFL.
- **Noto Sans.** Також OFL 1.1, прочитано в `google/fonts/ofl/notosans/OFL.txt`. Це запасний варіант, у реєстр його не вношу.
- **Що дозволяє текст OFL.** Шрифт можна вбудовувати й постачати з програмою. Вимоги ліцензії на створений документ вона не поширює. Вимоги до нас: шрифт без змін і без перейменування, поруч лежить `OFL.txt` з копірайтом, самостійно шрифт не продається.
- **Чому Roboto.** Він менший, ніж Noto, і містить кирилицю й ґ, є, ї, і.
- **Статичний, не змінний (variable) TTF.** Підтримку змінних шрифтів у PDFBox-Android 2.0.27.0 я не перевіряв, тому беремо статичний Regular.
- **Не перевірено:** точну назву й розмір файлу в `ofl/roboto/static` (запит до GitHub API заблоковано), чи працює `PDType0Font.load` з підмножиною в pdfbox-android 2.0.27.0. Це перевіряє тест: кирилиця має вилучатися через `PDFTextStripper` і малюватися в PDFium на пристрої.
- **Чому ✓/✗ без шрифту.** У Roboto цих символів, імовірно, немає (**НЕ ПЕРЕВІРЕНО**), а лінії надійніші й коштують $0.
- **Відкрите питання:** чи є в застосунку екран ліцензій. Для OFL і Apache потрібні копії текстів ліцензій. Агент має перевірити це в коді (**НЕ ПЕРЕВІРЕНО**).

### 3. cropBox і /Rotate

Перетворення, які ви навели, збігаються з моїм виведенням для 0° і 90°. Мої виведення для інших кутів, де W і H розміри CropBox до повороту:

- **0°:** x = llx + xv, y = ury − yv
- **90°:** x = llx + yv, y = lly + xv
- **180°:** x = llx + W − xv, y = lly + yv
- **270°:** x = llx + W − yv, y = lly + H − xv

180° і 270° я вивів лише математично, тому вони **НЕ ПЕРЕВІРЕНО** на пристрої й обов'язково йдуть у тести. Два додаткових зауваження:

- **Повернуті сторінки.** Текст і позначки на сторінці з `/Rotate` треба малювати з матрицею повороту, інакше вони стоятимуть боком. У поточному `addFreeText` цього немає.
- **Нормалізація `/Rotate`.** Значення бувають від'ємними й успадковуються від батьківського вузла. Кут треба привести до 0/90/180/270.

### 4. Перезавантаження

Усі чотири наявні діалоги збереження (текст, підпис, малювання, форми) використовують `documentUri = null; documentUri = savedUri` з тим самим URI. За спайком це нічого не оновлює. Отже, у поточній збірці збережене, імовірно, **не відображається**. У журналі це записано як «ймовірно, не перевірено на застосунку».

Що тестує Етап 0 (два способи отримати «новий URI»):

- **a)** той самий SAF-URI з унікальним фрагментом `#v2`. Фрагмент зазвичай ігнорується при відкритті, тож копіювати файл не треба. Це моє припущення, **НЕ ПЕРЕВІРЕНО**.
- **b)** копія в кеш застосунку з унікальним іменем.

Потім перевіряємо, чи відновлюється позиція після `onLoadDocumentSuccess`. Мінімум, який я прийму: та сама сторінка. Бажано ще й zoom і скрол. Якщо відновлюються лише сторінка, а zoom скидається, це рішення власника.

### 5. Android 9–11

Погоджуюсь, що не блокує розробку. Але функція, не перевірена на заявленому minSdk 28, може просто падати. Тому перед першим завантаженням у Play потрібен запуск на емуляторі API 28 і 30: відкрити, поставити позначку, зберегти. Якщо не працює, ховаємо розміщення на тих версіях.

### 1.5 Розміщення на сторінці

**Простір координат `PageViewPoint`:** одиниці — pt; початок — лівий верхній кут видимої області сторінки (CropBox після /Rotate); x вправо, y вниз. Це те, що повертає `PdfView.viewToPdfPoint`. `pageIndex` береться з `PdfPoint.pageNum`, НЕ з `firstVisiblePage`. Перетворення в простір користувача PDF (CropBox, /Rotate 0/90/180/270) виконує лише `core-pdf`; UI про поворот і CropBox не знає.

```kotlin
package com.savoj.volumpdf.core.pdf.model

enum class MarkKind { CHECK, CROSS }

sealed interface PageMarkup {
    val id: String
    val pageIndex: Int // 0-based (НЕ ПЕРЕВІРЕНО: звірити з PdfPoint.pageNum зі спайку)

    // (x, y) — лівий верхній кут рамки тексту
    data class Text(
        override val id: String, override val pageIndex: Int,
        val x: Float, val y: Float,
        val text: String, val fontSizePt: Float = 14f, val color: Int
    ) : PageMarkup

    // (x, y) — центр позначки; малюється векторно, без шрифту
    data class Mark(
        override val id: String, override val pageIndex: Int,
        val x: Float, val y: Float,
        val kind: MarkKind, val sizePt: Float = 16f, val color: Int
    ) : PageMarkup

    // точки штрихів — у PageViewPoint-просторі сторінки pageIndex
    data class Ink(
        override val id: String, override val pageIndex: Int,
        val strokes: List<InkStroke>
    ) : PageMarkup

    // (left, top, width, height) — у PageViewPoint-просторі
    data class Signature(
        override val id: String, override val pageIndex: Int,
        val bitmap: android.graphics.Bitmap,
        val left: Float, val top: Float, val width: Float, val height: Float
    ) : PageMarkup
}
```
