# Anti PDF — план реалізації редизайну

> Дата: 2026-11-23. План не змінює опубліковану або тестову збірку. Кожен етап виконується в окремій гілці, проходить незалежний QA до злиття та не потрапляє в Google Play без окремих воріт проєкту.

## 1. Стратегія

Редизайн впроваджується вертикальними зрізами: один завершений користувацький потік за раз. Не створюється «велика гілка», яка одночасно змінює весь застосунок. На кожному зрізі зберігаються функції, контракти PDF-ядра, SAF і наявні рекламні правила.

## 3. Деталізація етапів

### D0 — дизайн-база

- Зафіксувати фактичну карту функцій і суперечності документації.
- Затвердити термінологію та групування.
- Перетворити дизайн на перевірні acceptance criteria.
- Провести незалежний QA документів.

### D1 — фундамент

- Винести семантичні кольори, відступи, радіуси та розміри цілей дотику в ресурси.
- Створити єдиний спосіб застосування status/navigation/IME inset-ів.
- Замінити проблемний готовий екран Google OSS на власні список і деталі, використовуючи наявні дані ліцензій.
- Додати screenshot/інструментальні перевірки критичних системних відступів, якщо поточний стек це дозволяє без нової залежності.

### D2 — Бібліотека

- Оновити app bar, пошук і панель сортування.
- Уніфікувати рядок документа, обране, empty/no-results/error states.
- Зберегти Open PDF як головну дію; Create/Scan — вторинні.
- Перевірити зарезервовану зону banner ad і навігацію при клавіатурі.

### D3 — Інструменти

- Додати групи Create / Pages / Enhance у модель представлення без зміни `ToolType`.
- Зберегти всі 11 типів і їхні маршрути.
- Використати однакові назви з reader tools sheet.

### D4 — операції

- Побудувати спільні блоки: input picker, option section, validation message, sticky primary action, progress, result.
- Мігрувати інструменти по одному; старий маршрут лишається до завершення перевірки нового.
- Не змінювати файлові контракти або `core-pdf` без окремого архітектурного рішення.
- Зберегти дозволене розміщення banner у `ToolsActivity`, але приховувати його на час фактичного збереження/блокувального прогресу й не ставити поруч із sticky primary action.

### D5 — читач

- Відділити стан chrome від стану документа.
- Упорядкувати overflow-команди за режимом читання.
- Перевірити всі переходи: back, system back, rotation, process recreation, password, permission loss.

### D6 — редактор

- Замінити прокручувану панель на шість стабільних позицій.
- Перенести Delete до контексту вибору; Redo/Options — у More на вузьких екранах.
- Зберегти всі наявні стани selection pill, текстового редактора, клавіатури й незбережених змін.
- Перед міграцією скласти regression-набір для кожного типу розмітки.

### D7 — форми та сторінки

- Уніфікувати back/save/discard поведінку.
- Додати явний режим множинного вибору в організаторі.
- Перевірити довгі документи, великі мініатюри, скасування та помилки пам’яті.

### D8 — завершення

- Окремий Settings/About екран.
- Оновлений онбординг без зміни порядку UMP.
- Ресурси для compact/medium/expanded widths.
- TalkBack, switch access, high contrast, 100–200% font, RTL layout sanity check (без обіцянки локалізації RTL).

## 4. Правила міграції

1. Бізнес-логіка не переноситься в View/Adapter заради швидкості верстки.
2. Стан операції зберігається у ViewModel або наявному контролері; layout не стає джерелом правди.
3. Ідентифікатори аналітики не додаються; нових дозволів немає.
4. Старий і новий UI не змішуються в одному користувацькому потоці довше одного етапу.
5. Ресурсні рядки додаються одразу для всіх підтримуваних мов або етап не готовий.
6. У кожному PR є перелік функцій до/після і доказ відсутності втрат.
7. Автор змін не ставить `QA Verified`.

## 5. Перевірки для кожного кодового етапу

- `:app:assembleDebug`, `:app:testDebugUnitTest`, `:core-pdf:test` на JDK 21;
- числа тестів беруться лише з XML-звітів Gradle;
- перевірка конфлікт-маркерів і секретів;
- ручний smoke на Galaxy S24 Ultra для зміненого потоку;
- щонайменше Android 9/11 емулятор для edge-to-edge та системного back;
- світла/темна тема, 100% і 150% шрифт, портрет/ландшафт;
- окремий незалежний QA-запис до злиття.

## 6. Порядок релізу

- Дизайн-документи можуть бути злиті без зміни APK після незалежного QA.
- Код редизайну не підміняє активну збірку 14-денного закритого тесту.
- Перший кандидат редизайну проходить повний regression і новий внутрішній/закритий тест згідно з актуальними правилами Play та рішенням Власника.
- Жодної публікації, зміни Play Console або рекламної конфігурації в межах цього плану.
