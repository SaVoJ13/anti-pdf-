## 1. Критичний дефект: читач зависає (К)

Симптом: після відкриття будь-якого PDF (через системний вибір «Відкрити PDF», документ редагований, не лише читання) у ReaderActivity показується спіннер, лічильник «1 / 1», 100 %, сторінка не з'являється. Через 60+ секунд без змін. Падіння в logcat немає, виключень немає.

Відтворення (стабільно, 5 з 5 на збірці гілки, у тому числі після `adb uninstall` + чисте встановлення і після повторної збірки з нуля):

2. «Відкрити PDF» → вибрати будь-який простий PDF (3 сторінки).
3. Читач: вічний спіннер.

Порівняння (A/B на тому самому телефоні, тому самому файлі, тому самому способі відкриття):
- збірка `origin/main` (27bc1cf): документ відкривається одразу, «Стор. 1 з 3», сторінки малюються (2 з 2);
- збірка гілки: зависання (5 з 5).

Локалізація (діагностика, не виправлення): якщо тимчасово прибрати з `VolumPdfApp.onCreate` блок `DynamicColors.applyToActivitiesIfAvailable(...)` (разом із `AppearancePreferences`), читач у збірці гілки відкриває документ нормально (перевірено). Якщо лише прибрати `android:resizeableActivity="true"`, зависання лишається. Тобто причина майже напевно в реєстрації DynamicColors у Application (навіть при вимкненому перемикачі), ймовірно взаємодія з вбудованим переглядачем PDF/його Activity-колбеками. Точний механізм не з'ясовано (стек потоків недоступний без root).

Автор це не помітив, бо на JVM-тестах такого не видно. Чому попередній QA не побачив: телефон був заблокований.

Вимога до автора: виправити так, щоб читач завантажувався; повторити відкриття документа на пристрої; додати в `docs/qa` перевірку відкриття PDF у читачі як обов'язковий пункт для змін `VolumPdfApp`/тем.

### 3.1 Колонки (НАЙГОЛОВНІШЕ): підтверджено на пристрої

Формула AdaptiveLayoutLogic: колонки = floor(ширина списку в dp / 340), 1..3 для «Останніх» і «Інструментів»; 170 dp, до 6, для організатора; вміст обмежено 840 dp.

| Екран | Ширина вікна | Останні | Інструменти | Організатор |
|---|---|---|---|---|
| Телефон, портрет | ≈411 dp | 1 колонка (список 1328 px = 379 dp) | 1 колонка | 2 колонки |
| Телефон, ландшафт | ≈891 dp (>840, обмежено) | 2 колонки (по ≈387 dp), вміст ≈775 dp по центру | 2 колонки | не міряв |
| Емуляція планшета `wm size 1600x2560` + `wm density 280` | ≈914 dp | 2 колонки (по ≈696 px), список 1414 px = 808 dp, поля по 93 px з обох боків (вміст центрований, не ширший за 840 dp) | 2 колонки (693 px), ширина 800 dp, по центру | 5 колонок (914/170=5,4) |

Збігається з формулою й очікуванням 808 dp / 340 = 2. Причина «1 колонки на 914 dp» у ранній збірці автора: не відтворена в фінальній збірці (на 914 dp стабільно 2 колонки у «Останніх» і «Інструментах», 5 в організаторі). Це узгоджується з поясненням попереднього QA (слухач до першого вимірювання), підтвердження на пристрої: фінальна збірка колонки рахує правильно. Ширина обмежується 840 dp.
Після змін `wm size reset` і `wm density 560` виконано, початкові значення перевірено.

Під час зміни розміру/щільності екрана організатор з відкритим документом перебудувався без падіння (5 колонок). Збереження порядку сторінок посеред жесту саме при зміні розміру не перевіряв.

### 3.5 Не перевірено (причина)

- Split-screen (`am start --windowingMode`, ручний multi-window): НЕ ПЕРЕВІРЕНО: у середині роботи на телефон стала виходити на передній план сторонній застосунок (`com.savoj.boilerwidget`), кілька моїх тапів пішли йому наосліп (див. гігієну), а читач гілки у будь-якому разі не відкривається.
- Зміна розміру вікна читача без втрати стану (`resizeableActivity=true`): НЕ ПЕРЕВІРЕНО на збірці гілки (п. 1). У збірці без блоку DynamicColors: 5 циклів повороту (ландшафт/портрет) із відкритим документом у режимі редагування: процес живий, документ і режим редагування збереглися.
- Регресія читання, редагування → зберегти, пошук на збірці гілки: НЕ ПЕРЕВІРЕНО (п. 1). На збірці main відкриття документа працює.
- Поворот 5 циклів із відкритими картками: частково (див. вище, без відкритих карток).
- Темна/світла тема для екранів читача та організатора з динамічними кольорами: НЕ ПЕРЕВІРЕНО.
